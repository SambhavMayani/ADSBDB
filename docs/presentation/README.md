## Decisions and report examples

**Slide 5 lists all 16 steps in order**, grouped by stage. It is a sequential process flow, not parallel execution or a formal Petri net. Storage checks and bucket creation come first, followed by local ingest and the verified Persistent copy, three formatters, three validators, five indexers and final reconciliation. The indexing order is images, text, audio, image/text, audio/text. Optional acquisition adds three downloads after storage setup (19 steps). Follow the groups during the talk rather than reading every label. The same numbered list appears in the report and [orchestration guide](../pipeline_orchestration.md).

Slide 6 distinguishes **SHA-256 hashes from embeddings**: byte fingerprints support identity/integrity, while model vectors support similarity. The recompression example is conceptual rather than a new inference measurement.

Slide 7 shows the concrete **Landing** identity: `temporal_landing/<SHA-256[:16]>__<filename>`. Temporal reuse checks source identity. When Temporal is absent, an independent completion record identifies a Persistent target. A compatible marker and existing target permit skipping; no marker means a new ingest; conflicts or broken targets fail. The copy step verifies bytes before writing completion. This record confirms the Persistent copy, not Trusted acceptance. The slide and speech use that plain description instead of “promotion”. Renaming changes technical ingest identity; Trusted applies content deduplication separately.

Slide 8 illustrates all four **Landing name/content combinations** with two existing photographs, abbreviated hashes and illustrative filenames. With compatible source metadata and an existing Temporal object or valid completion record: same bytes + same name skips; same bytes + different name enters; different bytes + same name enters under another key, preserving the first object; changing both enters too. Hashes shown refer to the embedded example bytes, not the original raw-data names. The script explains why a renamed copy enters: the source-file identity includes the name, and preserving that record costs extra storage. Trusted handles duplicate content afterwards. SHA-256 is not LSH. A changed file may look unchanged, and a truncated hash prefix is not a mathematical collision-free guarantee.

Slide 9 justifies **Formatted** choices: RGB JPEG at quality 95 for a detail/file-size compromise in wildlife photographs; FLAC PCM16 to avoid extra lossy compression of faint calls among rain, wind or other animals; UTF-8/LF/NFC for multilingual descriptions. JPEG is usually compact for photographs, not universally smaller. FLAC retains the selected PCM16 values and cannot restore previous losses. JSON first selects recognised content keys and only then falls back to the longest string. It explains MPO as several photos in one file: six reference containers contribute their first photo while the originals retain all frames. The speech explains dimensions, format alternatives, JPEG loss, PCM16 quantisation and extraction loss. Complete originals remain in Persistent. Model-specific cropping/resampling belongs in Exploitation; the zone guide retains the detailed transparency/EXIF policies.

Slide 10 explains **Trusted** quality rules and budgets: images 20 decimal MB, 40 MP and minimum 128 by 128; audio 200 MB; text 4 MB. These are operational thresholds. Warnings remain distinct from rejection, and later errors/rejections retain earlier accepted bytes.

## Task examples and validation

Slides 14–15 explain segment coverage, model-policy compatibility and why CLIP, CLAP and multilingual E5 serve different retrieval relationships. Counts alone do not establish complete indexing. Image/text comparisons use aligned CLIP encoders; audio/text comparisons use aligned CLAP encoders. Independent models do not share a comparable coordinate system. Federated retrieval combines their per-model positions using reciprocal rank fusion, not raw cosine scores.

Slide 16 explains cosine as the dot product divided by both vector lengths. The illustrative unit query `(1, 0)` gives scores 0.96, 0.60 and 0.00 against `(0.96, 0.28)`, `(0.60, 0.80)` and `(0, 1)`. This is a transparent two-dimensional calculation; production vectors have 384 or 512 dimensions. Higher scores mean closer alignment within a compatible space, without a universal relevance threshold or species probability.

Slide 17 names the configured search algorithm: **HNSW (Hierarchical Navigable Small World)** in Chroma, with cosine distance. Its editable schematic shows sparse upper layers and refinement at denser lower layers. The diagram is conceptual, not a measured graph traversal. The code uses an exhaustive exact comparison when the eligible set has at most 64 vectors; 65 or more delegate to Chroma. The cap keeps the fallback small and supports tiny segments without a persisted graph. It is not an optimum established by benchmarking 32, 64 and 128. New tests cover 64/65 with and without filters. Course references in notes: supplied *5 - Vector Databases.pdf*, pages 31–34 (exact nearest-neighbour scan/ANN) and 87–105 (HNSW). HNSW is approximate and may miss a true neighbour. We make no measured recall or speedup claim, and do not implement PQ, LSH or IVF for retrieval. Chroma implements HNSW; EcoSentinel configures and queries it.

Slide 18 shows actual Task 1 matches at ranks 1 and 3, with the full five-asset ranking retained in the JSON. Four catalogue labels are lynx and one is wolf; rank 2 is a cropped variant.
