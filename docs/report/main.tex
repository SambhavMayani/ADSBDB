\section*{User manual / 1 of 2}
Repository \url{https://github.com/SambhavMayani/ADSBDB}\\
Authors Mario Rodrigo, Sambhav and Wassim.

These instructions use Windows and Git Bash, from the repository folder. Install 64-bit Python 3.11, Git and Docker Desktop first, then start Docker Desktop. You need Internet to install libraries and download models. Inference runs on CPU. No GPU or paid AI API is required. Linux instructions are in \path{README.md}.

\subsection*{1. Install the application and check the code}
\begin{Verbatim}
git clone https://github.com/SambhavMayani/ADSBDB.git
cd ADSBDB
python -m venv .venv
source .venv/Scripts/activate
python -m pip install -r requirements.txt
python -m pip check
python -m pytest -q
python -m orchestration.pipeline --plan
\end{Verbatim}
The tests should pass. The plan lists 16 steps without running them. Neither command needs your wildlife data or model weights. In each new terminal, return to this folder and activate \texttt{.venv} again. If the repository is private, the assessor needs access.

\subsection*{2. Download the pretrained models once}
Libraries contain the code. Model weights are the learned parameters that the code loads to process an image, sound or text. Downloading them does not train a model or create dataset embeddings. Prepare the embedding models before running the pipeline.
\begin{Verbatim}
python -m exploitation_zone.prepare_models --download
\end{Verbatim}
Expect \texttt{Embedding models ready}. For Task 3 only, also prepare Qwen and BLIP.
\begin{Verbatim}[fontsize=\footnotesize]
python -m multimodal_tasks.rag_model --download
HF_HUB_OFFLINE=0 python -c "from huggingface_hub import snapshot_download; \
from multimodal_tasks.generate import MODEL, REVISION; \
snapshot_download(repo_id=MODEL, revision=REVISION, token=False)"
\end{Verbatim}
Later runs reuse the local cache. The pipeline loads weights offline. Its acquisition option downloads \emph{wildlife data}, not models. Task 3 checks for 2.5 GiB of available RAM before generation. This is a guard, not a full machine specification. Close other applications if needed and allow minutes for CPU responses. Keep free disk space for weights, data and the query copy.

\subsection*{3. Start local object storage}
\begin{Verbatim}
cp -n .env.example .env
# Edit .env: set your local storage username and password.
docker compose up -d
python orchestration/check_minio_connection.py
\end{Verbatim}
Set \texttt{MINIO\_ROOT\_USER} and \texttt{MINIO\_ROOT\_PASSWORD} before creating a new storage service. Keep existing credentials when using a prepared installation. Never commit \texttt{.env}. Port 9000 is the S3 API and port 9001 is the storage console. The EcoSentinel interface uses a different port, shown on the next page.

\section*{User manual / 2 of 2}
\subsection*{4. Choose the route that matches your data}
A. Starting without local raw data. Set the provider credentials in \texttt{.env}, including \texttt{XENO\_CANTO\_API\_KEY}, and review the species/acquisition settings in \texttt{config/}. Then run the following command.
\begin{Verbatim}
python -m orchestration.pipeline --run --with-acquisition
\end{Verbatim}
This runs three download scripts and then the normal pipeline, making 19 steps in total. Providers can change content or impose quotas. The default audio request is four recordings per species, and shortages can stop acquisition. Inspect the log and keep successful downloads. If you decide to use the available smaller dataset, review its metadata and continue with route B. A fresh download need not reproduce our reference counts.

B. Raw data already supplied locally. Place the files and their matching \texttt{\_metadata.json} records under \path{data/raw_dataset/<modality>/<species_id>/}. Use the supplied/acquisition layout, since arbitrary files without provenance are insufficient. Run the following command.
\begin{Verbatim}
python -m orchestration.pipeline --run
\end{Verbatim}
Expect \texttt{Pipeline status: completed}. The last step checks that accepted files and vector segments agree. Logs and the run JSON are under \path{reports/orchestration/}.

C. Storage and Chroma already prepared. Keep their matching data and model cache. Skip rebuilding and run \texttt{python -m orchestration.reconcile}. Expect \texttt{completed} and an empty \texttt{problems} list. Only the unchanged reference installation should have 198 accepted files and 6,021 vectors. Git contains neither that dataset nor the weights.

\subsection*{5. Prepare searches and open the interface}
Stop pipeline/index writers first. Use a new, nonexistent destination.
\begin{Verbatim}
python -m orchestration.audit --source data/chromadb \
  --snapshot data/search_index
python -m multimodal_tasks.search --status
python -m webapp.server
\end{Verbatim}
The first command verifies and copies the existing database. It does not run encoders again or copy media. Chroma already persists vectors on disk, but opening it can cause internal writes. Our interface therefore opens this separate copy to protect the original. The copy costs extra disk space and does not update itself. Reuse it while the data is unchanged. After an index update, create a new copy and pass its path with \texttt{-{}-index NEW\_PATH} to the search/web commands.

Open http://127.0.0.1:8765. The pipeline does not start the web automatically. Try an image in \emph{Buscar similares} for Task 1, a wildlife phrase in \emph{Explorar por texto} with mixed results for Task 2, and a habitat/diet question in the RAG tab for Task 3. Check the sources. Search quantity defaults to eight files and can be set to 1--50. CLI searches use \texttt{-{}-limit N}. Stop the server with Ctrl+C.

\subsection*{6. Inspect what the run produced}
Open \path{reports/trusted_quality/<modality>/<timestamp>/quality_report.html}. Keep its PNG files beside it. The same folder contains JSON summaries and CSV measurements. Expected results and recovery steps for all routes are in \path{docs/user_guide.md}. A run that fails a check needs investigation before its results can be accepted.

\subsection*{About this project}
EcoSentinel brings wildlife photographs, recordings and descriptions into one local system. We preserve the original files, check their quality and make them searchable. Users can find related material and ask questions whose answers point back to retrieved sources.

Our main goal was to build a clear, reliable and testable pipeline. Wildlife gives the work a practical setting, but this project does not claim expert species recognition. The manual comes first so that a new reader can install the application, run the pipeline and inspect its results. Eight pages explain the design and evidence, followed by a separate query-flow appendix.

\section*{1. Purpose, data and architecture}
\subsection*{Why wildlife data?}
A field team may need a photograph, an animal call and a description of its habitat, yet these materials often sit in separate catalogues. We chose Iberian fauna to explore how one system could connect them. Our priority for P1 was the code, pipeline design and validation, rather than optimising biological results. We still used the domain to guide decisions that would matter with more data and models.

EcoSentinel could help teachers prepare wildlife lessons or help analysts review material related to an observation. A user can start with a file or a phrase, find related records and follow an answer back to its source. The intended value is less manual searching across catalogues. We have not measured time savings or tested a commercial service. Reliable species identification would also require expert evaluation.

\subsection*{What the reference dataset contains}
\begin{tabularx}{\linewidth}{@{}l r Y@{}}\toprule
Type & Files & Sources\\\midrule
Images & 100 & Wikimedia Commons, ten images per species\\
Audio & 34 & Xeno-canto, recordings for nine species\\
Text & 64 & 20 Wikipedia articles and 44 GBIF descriptions\\\bottomrule
\end{tabularx}

The ten species include the Iberian lynx, wolf, deer, wild boar, eagle, eagle owl, kingfisher, robin, Perez's frog and ocellated lizard. Scientific identifiers in \path{config/species.yaml} link records across zones. Audio adds a useful ecological view, but coverage is uneven because the lizard has no recording and the lynx has only two. Text also varies by species and source. We keep these gaps visible instead of treating the sample as representative of Iberian biodiversity.

The acquisition scripts save URLs, provider identifiers and available licence/attribution fields beside each raw file. Wikipedia records also retain revision information. Provider labels help trace the data, but they are not expert checks of the species. Some audio licences restrict commercial reuse, so any future business use would need to review permissions for each asset.

Each zone answers a different about arrival, representation, usability and search. This separation lets us change a quality rule or encoder without losing the original evidence. Python packages follow these boundaries. S3 object storage suits the large, varied media files, and separate buckets distinguish their processing state. Chroma stores vectors locally without requiring another database server. The Docker configuration pins the S3-compatible storage service.

One orchestrator connects independently testable stages. One of our laptops had no suitable GPU, so we chose CPU as the common setup for the whole group. Models load sequentially to limit RAM use. Acquisition remains optional, allowing supplied data to follow the same route without another download.

\section*{2. Landing and Formatted}
\subsection*{Simple checks before expensive processing}
We added the Security Gate to reject obvious risks before decoding or running models. It checks allowed types, byte signatures, file size, image dimensions and archive limits. For example, an executable renamed as a photograph is rejected from its header, while an oversized file stops before costly processing. These are practical input heuristics, not an antivirus scanner. Accepted files enter Temporal Landing and are then copied and verified in Persistent Landing, by modality and species.

The Temporal key combines the first 16 hexadecimal characters of SHA-256 with the filename. SHA-256 reads raw bytes in small blocks without loading a decoder or neural model. This makes it a cheaper first check than computing an embedding, although we have not measured a speed ratio. A hash detects byte identity and supports integrity checks, while an embedding measures similarity in learned features.

\begin{tabularx}{\linewidth}{@{}l l Y@{}}\toprule
Bytes & Name & Landing result\\\midrule
Same & Same & Reuse the existing, verified record\\
Same & Different & Ingest a separate submitted-file record\\
Different & Same & Use a new hash and preserve the earlier file\\
Different & Different & Ingest a new record\\\bottomrule
\end{tabularx}

We debated using only the content hash. Keeping the name also preserves the identity of each submitted file, so renamed copies remain traceable at ingestion. We accepted the extra storage and left content duplicate removal to Trusted. A filename is not proof of a different source. The shortened key can collide, so copy verification uses the full SHA-256, metadata and byte length.

A completion record is written only after copy verification. If a file has left Temporal, a rerun checks that record and its Persistent target before skipping it. Missing targets or conflicting species/source metadata cause an error. Temporal files are retained by default, allowing interrupted copies to recover. This record confirms Landing completion, not Trusted acceptance.

\subsection*{Formats chosen for our wildlife data}
Images become RGB JPEG at quality 95. Photographs contain colour gradients and texture, which JPEG usually stores more compactly than lossless PNG. Quality 95 is our conservative size/detail compromise, not a measured optimum. Dimensions and EXIF orientation are kept without rotating or cropping, and transparency becomes white. JPEG is lossy, so we retain the original.

MPO contains several photographs, even when named \texttt{.jpg}. We choose frame 0 as a consistent single-image view. Extra frames can be alternative views of one scene, so indexing all of them could overrepresent it. We do not assume every MPO frame is a duplicate or that frame 0 is always its representative image. Keeping one asset per source also avoids introducing derived-frame provenance and licence links. Six files yield six JPEGs, while all eight additional frames remain in the Persistent originals.

After listening to the recordings, we found that rain, wind and other animals commonly overlap with the target call. We chose FLAC PCM16 to avoid another lossy audio codec and retain that sound. FLAC compresses the resulting PCM samples losslessly, usually saving space over uncompressed PCM. Rate, channels and quiet intervals are preserved. Conversion to 16-bit can reduce precision, and FLAC cannot recover earlier MP3 losses. Model-specific resampling happens later.

Text becomes UTF-8 with NFC characters and LF endings, retaining case and punctuation. For JSON, we first look for content fields such as \texttt{text}, \texttt{body} or \texttt{description}, preferring those closest to the root and using a fixed priority for ties. If none is found, we take the longest non-empty string. The idea is that a description is often longer than a title or identifier, but this heuristic can select the wrong field. Arrays are handled per record. We save the extraction method/path and retain the original structure upstream.
\refguide{\path{docs/landing_zone_documentation.md}, \path{docs/formatted_zone_documentation.md}.}

\section*{3. Trusted decisions and quality reports}
Trusted checks usability and provenance before choosing a search model. Policies live in YAML so that the rules and their versions can be inspected. A technical failure can reject a file. A warning records uncertainty while keeping potentially useful material.

\begin{tabularx}{\linewidth}{@{}p{.14\linewidth}Y Y@{}}\toprule
Type & Checks and decisions & Reason\\\midrule
Images & Decoding and provenance. Limits of 20 MB and 40 MP, with at least 128 pixels per side. Exact hashes, then pHash candidates checked with structure/colour. & Compressed size alone cannot bound decoding memory. Very small images have little usable detail. Duplicate confirmation is stricter than a perceptual hash alone.\\
Audio & Decoding and provenance, 200 MB cap, duration and amplitude, exact PCM duplicates. & Recordings can be longer than image files. Quiet or distant calls may still be useful, so low energy produces a warning.\\
Text & Strict decoding and provenance, 4 MB cap, exact duplicates, near-duplicate warnings and privacy-pattern counts. & Species descriptions should remain manageable. Short GBIF records and long articles need different interpretation, not an arbitrary common length.\\\bottomrule
\end{tabularx}

These byte limits use decimal MB. They are operational budgets for this local prototype, not biological boundaries or values proven optimal by experiments. Pixel limits complement byte limits. Audio memory also depends on duration and decoding, so its byte cap cannot guarantee a fixed RAM peak. The policies can be revised with measurements on a larger dataset.

We chose warnings over blanket rejection for darkness, blur, monochrome images and possible watermarks. Field captures are often imperfect, yet a rare animal observation may still be valuable. Our watermark heuristic has no labelled accuracy evaluation and may flag useful images, including those with a small mark. Reports let the organisation review these cases rather than silently discard them. We also keep background sound and quiet intervals, since cropping or denoising could change the evidence.

A later failure or rejection keeps previously accepted bytes and records the changed status. Reconciliation exposes outdated index references instead of silently deleting data.

\subsection*{Reports explain the decision for each file}
Each check produces JSON under \path{trusted-zone/_quality/<modality>/}, including the source, policy, decision, reasons and measurements. Report generators aggregate the current stored records, including earlier runs. They do not decode every file again or change acceptance decisions.

The local output includes an HTML report, a JSON summary, a CSV table and PNG charts. Images record dimensions, megapixels, size, brightness, sharpness and aspect ratio. Audio records duration, sample rate, channels, RMS/peak level, clipping and low-energy frames. Text records characters, words, vocabulary ratios and privacy-pattern counts without publishing the matched private values. Statistics and plots expose long files, quality warnings and uneven coverage. Before/after species distributions and source-field completeness help show whether filtering changed the collection.

\subsection*{What the reference reports show}
All 198 reference files remain accepted. The image report flags 32 possible watermarks and 14 monochrome-like images. These are heuristic flags, not confirmed defects. Audio has nine low-energy and two low-RMS flags. Its median duration is 40.91 seconds and its longest recording is 752.37 seconds. Text has a median of 208.5 words, ranging from 33 to 13,869. Source-field completeness is 100\%, but populated fields do not prove correct labels. Species distributions remain unchanged, including the missing lizard audio.

These results describe a curated batch. Synthetic malformed files and fault tests exercise rejection separately. We still need labelled examples to measure watermark and duplicate-detection accuracy. Pairwise text comparison will also need a more efficient candidate index as the dataset grows.
\refguide{\path{docs/trusted_zone_documentation.md} and reference summaries in \path{docs/evidence/quality_*.json}.}

\section*{4. Exploitation and model choices}
An embedding is a list of numbers that a model uses to represent content. Similar meanings can produce nearby vectors, even when file bytes differ. Exploitation creates these vectors from accepted Trusted files and stores them in five Chroma collections.

\begin{tabularx}{\linewidth}{@{}Y l r r@{}}\toprule
Collection & Model family & Dimensions & Vectors\\\midrule
Images & CLIP & 512 & 100\\
Audio & CLAP & 512 & 357\\
Text & Multilingual E5 & 384 & 547\\
Image and text & CLIP-aligned & 512 & 1,763\\
Audio and text & CLAP & 512 & 3,254\\\midrule
Total & & & 6,021\\\bottomrule
\end{tabularx}

\subsection*{Models selected for the tasks and our hardware}
CLIP ViT-B/32 is a well-established image/text model with a manageable base-size encoder. It supports visual and text-to-image search without training a classifier for our ten species. Its image processor resizes and centre-crops to $224\times224$ pixels, which can lose fine markings or small animals. This is a model step, not a change to Trusted images. We accepted that limit for a retrieval prototype, without claiming species-level accuracy.\footnote{The pinned \href{https://huggingface.co/sentence-transformers/clip-ViT-B-32/blob/327ab6726d33c0e22f920c83f2ff9e4bd38ca37f/0_CLIPModel/preprocessor_config.json}{CLIP processor configuration} specifies the resize and crop.}

Some descriptions are in Spanish, and Iberian fauna is our domain. We therefore use the multilingual CLIP text adapter aligned with the image encoder, allowing Spanish and English queries in the same space. CLAP HTSAT-unfused provides a separate shared audio/text space for matching calls to descriptions. Multilingual E5-small handles text retrieval with its required \texttt{query:} and \texttt{passage:} prefixes, keeping this part small enough for CPU use.

Each model supplies a trained relationship that the others do not. Running them sequentially avoids keeping every model in RAM. We chose practical, reusable encoders, not winners of a wildlife benchmark. Exact identifiers and pinned revisions are in \path{config/model_manifest.json}.

\subsection*{Why 6,021 vectors for only 198 files?}
Long inputs need smaller parts because encoders have limited input lengths. E5 uses text chunks of 320 tokens with 40-token overlap. The image/text route uses 96 with 12-token overlap, and the audio/text route uses 60 with eight-token overlap. These budgets suit their configured text encoders. Overlap reduces the risk of splitting a useful sentence at a boundary, at the cost of extra vectors.

Audio uses ten-second windows after encoder preparation to 48 kHz mono. A window keeps a local call searchable instead of averaging a long recording into one vector. This step belongs to the model, so Trusted can retain the original rate and channels for other uses. Text also appears in shared collections, which explains much of the extra vector count. Results later group segments back into files.

\subsection*{Persistent, incremental indexing}
Vectors remain on disk in \path{data/chromadb/}. Metadata links each part to its source file, model/policy version and position. An unchanged file with all expected parts is skipped on a rerun. Source checksums, policy fingerprints and complete part sets determine reuse. A matching total count alone is insufficient. Interrupted publication can be repaired by processing the incomplete asset again.

The indexer loads models sequentially on CPU and uses bounded batches. This reduces simultaneous memory use, although long audio still needs care during decoding. The application opens a verified query copy rather than the original database because Chroma may write internal state when opened. Copying stored vectors is inexpensive compared with computing them again, but takes disk space and must be repeated after updates. It protects the original index, but it is not required to make vectors persistent.
\refguide{\path{docs/exploitation_zone_documentation.md}, \path{docs/data_sources.md}, \path{config/exploitation.yaml}.}

\section*{5. Similarity search and its limits}
\subsection*{Cosine measures direction in one vector space}
For two non-zero vectors, cosine similarity is
\[
  s(q,x)=\frac{q\cdot x}{\lVert q\rVert\lVert x\rVert}.
\]
We normalise both vectors, so this becomes a dot product. Values range from $-1$ to $1$, with larger values meaning closer directions. Chroma returns cosine distance, so we display $1-\text{distance}$. We reject non-finite or incompatible vectors rather than returning misleading scores.

For an illustrative query $q=(1,0)$, the unit vectors $(0.96,0.28)$, $(0.6,0.8)$ and $(0,1)$ score 0.96, 0.60 and 0.00. The first is closest in this example. These numbers are not probabilities that two animals share a species. Real scores depend on the model and query type, so there is no universal ``correct match'' threshold in our interface.

\subsection*{Exact search for small sets and HNSW for larger sets}
The application counts eligible vectors after filters. With 64 or fewer, it reads the vectors and compares every one. With 65 or more, it asks Chroma's HNSW index. HNSW, or Hierarchical Navigable Small World, is a graph search method that navigates from coarse graph levels to nearby candidates instead of comparing every vector. It is approximate, so it can miss an exact nearest neighbour.

Why choose 64? We wanted a small, bounded exact scan that also works for tiny or new Chroma segments without a persisted HNSW reader. At 512 dimensions, 64 dot products involve 32,768 vector components. The float32 vector payload alone is 128 KiB, excluding metadata, Python objects and normalisation work. This makes the scale of the fallback explicit. We did not benchmark 32, 64 and 128 to find an optimum. Another small cap could work, but changing it should follow timing and recall measurements. Tests cover both 64 and 65, including filtered collections. The cap counts vector parts, not returned files and not vector dimensions.

For larger sets, we expand the retrieved candidate pool when many matches belong to one file. We then keep distinct assets, so a long recording cannot fill the result list merely because it has many segments. Top-k means the maximum number of returned files, with a default of eight, selectable from 1 to 50 in the interface or with \texttt{-{}-limit N}. Filters or limited data can produce fewer results.

\subsection*{Different modalities need a shared trained space}
An image and a sentence can be compared when their encoders share a trained CLIP space. The same applies to CLAP audio and text. E5 lives in its own space. Even though CLIP and CLAP both produce 512 numbers, their coordinates mean different things. Computing their cosine would produce a number without a valid similarity interpretation, so we keep those collections separate.

When a query uses several spaces, reciprocal rank fusion (RRF) combines positions rather than raw cosine values. Each file receives $1/(60+r)$ from each ranking where it occurs at position $r$, counted once per ranking. The constant 60 smooths the advantage of the first few ranks. It is separate from top-k and has not been tuned on labelled wildlife queries. A visible modality allocation can then keep mixed results useful. This output is a combined ranking, not one global cosine ranking.

We therefore distinguish correct search mechanics from useful biological retrieval. Tests can verify filtering, grouping and score handling. Expert relevance labels are still needed to measure recall, ranking quality and species-related errors.
\refguide{\path{multimodal_tasks/search.py}, \path{docs/multimodal_tasks_documentation.md}.}

\section*{6. Tasks 1 and 2, queries and interface}
\subsection*{Task 1 / find similar material of the same type}
A photograph retrieves photographs, a recording retrieves recordings, and text uses E5 to retrieve descriptions. For a stored record, we reuse its vector and exclude that entire file from the results, including its other segments. For an upload, we prepare the bytes in memory and use the same encoder and vector normalisation as the indexed data.

This supports questions such as ``Which stored photographs look like this one?'' A high-ranking image may share colour, pose or background without showing the same species. The result cards expose the source and score so that the user can inspect the candidates rather than accept a biological label automatically.

\subsection*{Task 2 / search across types of material}
The image/text and audio/text collections each contain both types of data. A text phrase can retrieve photographs and descriptions through CLIP, or recordings and descriptions through CLAP. Image and audio queries can also retrieve mixed results in their compatible spaces. When searching all spaces, RRF combines the rankings as explained on page 5.

We group results by file and allocate available places across modalities. This helps a user see related evidence without a large number of text chunks taking every place. The trade-off is that the final order serves mixed exploration rather than pure cosine ranking. A heavily filtered search can still return only one modality.

\subsection*{Queries reuse processing without entering the dataset}
We debated whether uploads should pass every dataset check. After the supervisor's clarification, we chose comparable preparation while giving users more freedom over quality. Queries reuse the Formatted code for RGB JPEG quality 95, FLAC PCM16 and canonical text, followed by the same encoder preparation as indexing. Stored Trusted JPEGs bypass another JPEG encode. This reduces avoidable differences but cannot undo earlier compression or guarantee identical vectors from separately encoded files.

A field recording or photograph may be poor but still carry useful information. Shared Trusted measurements therefore report blur, darkness, small size or quiet audio as warnings. We omit duplicate rejection because a user may be searching for an existing file, and omit the uncalibrated watermark rule. Hard guards still reject invalid inputs, uploads above 10 MiB, images above 20 MP and audio above 30 seconds or eight channels before conversion. These tighter budgets bound interactive CPU work rather than define biological quality.

Uploads stay in memory and are not added to MinIO or Chroma. The response includes an input hash and preparation details for traceability. Quality warnings are visible to the user and stay outside the RAG prompt because a blur measurement is not evidence about an animal.

\subsection*{A local interface for all three Tasks}
\begin{tabularx}{\linewidth}{@{}p{.34\linewidth}Y@{}}\toprule
Tab & What the user can try\\\midrule
Explorar por texto & A text query in E5, either shared space or all spaces, with species filters and result quantity.\\
Buscar similares & An image or short recording for same-type or mixed retrieval, with related-file actions.\\
Preguntar al corpus / RAG & A question with an optional image, with cited claims, candidate species, quality notes and response status.\\\bottomrule
\end{tabularx}

Here, ``corpus'' simply means the stored collection of documents and media. The static frontend needs no separate build tool. The Python server binds to the local machine, checks host/origin and serialises CPU requests. This makes classroom setup simpler. A public multiuser service would need authentication and a different deployment design.

\section*{7. Task 3 / answers from retrieved evidence}
Task 3 uses retrieval augmented generation, or RAG. It retrieves stored information and gives selected passages to a language model, allowing answers to cite sources or decline questions with insufficient evidence.

\subsection*{How a question with an image is answered}
The image first receives the shared preparation on page 6. BLIP produces a caption, which passes a wildlife vocabulary check before retrieval. CLIP then searches the image/text collection for visual candidates. Their species names guide E5 searches for the requested subject, such as habitat or diet, with a bounded lexical search for explicit terms. Global text searches keep one candidate from deciding the answer. Without an image, the question passes the vocabulary check and uses E5 plus multilingual CLIP text retrieval. Appendix A shows both routes.

The selector keeps at most eight literal units and 1,600 characters to bound prompt size and CPU cost. Full references remain visible. The prompt requires evidence-based claims and uncertainty about the photographed animal. We avoid repeating a noisy caption in every biological search.

Qwen receives text, not image pixels. BLIP is the image-to-text step. Its caption can be wrong. In the recorded frog example it described ``a frog with a dumb barbell''. We treat this as a model observation, never as a verified identification. Similar frog references can still support a conditional answer about the retrieved candidates' habitat or diet.

\subsection*{Why Qwen and a separate captioning model?}
We use Qwen2.5-3B-Instruct in Q4\_K\_M GGUF form through llama.cpp. Quantisation reduces the model's memory needs, making CPU execution possible without a paid API. The model file is pinned and checked by SHA-256. BLIP gives us a separate image captioning step that we can inspect and test. This design loses some visual detail compared with a model that directly reads images, but keeps the components manageable on our machine. We have not established superiority over larger models or native visual assistants.

Generation uses a JSON grammar, then checks the response structure, allowed evidence IDs and exact quote matches. Multi-aspect questions can produce up to two claims. If one aspect has no support, it can remain empty and the interface reports a partial answer. These checks catch invented reference IDs and quotes. They do not prove that the model interpreted a passage correctly.

\subsection*{Failure handling and what we have validated}
We decided to bound generation to 320 tokens, 120 seconds and four CPU threads, with a 2.5 GiB available-RAM check. These choices keep requests manageable on our laptops. The vocabulary gate also avoids spending generation time on unrelated questions, such as cooking advice, which our wildlife sources cannot support. It checks the question without an image, or the BLIP caption with one, and may reject valid wording. This is a domain heuristic, not a reliable detector of every unfamiliar input.

An evidence-based abstention differs from invalid JSON, a timeout or an incomplete output. The interface exposes the status and retains any retrieved references. Both the gate and the subject-selection rules need broader language evaluation.

Earlier native checks exercised text habitat, stored-image habitat, conditional frog identification, an unsupported genome question and an unrelated request. A separate frog habitat/diet browser run took 131.8 seconds overall, including 76.1 seconds of generation. One lynx answer was less directly relevant. These runs show that the system can execute the workflow, but they are not an accuracy benchmark. The later query-preparation revision has offline regression tests, but those historical native runs were not repeated for it.

Further evaluation needs labelled external queries to measure relevant retrieval, unsupported answers and unnecessary abstentions.

\subsection*{Tests target behaviour and failure recovery}
On 4 November, 469 offline tests passed with 72.37\% statement coverage, using generated files, storage doubles, temporary real Chroma and local HTTP. Cases cover conversion, provenance, duplicates, query limits, citations and idempotence. Recovery tests check completion records, conflicting sources, interrupted storage, preserved outputs, rejected Trusted records and missing/stale vector parts. Search tests include the 64/65 boundary.

Coverage shows which statements ran, not accuracy or complete outcome checks. We kept the same measurement scope. Some paths require storage/model checks and others remain untested. Executing lines merely to reach 100\% would not establish better behaviour.

Isolated S3/Chroma integration also passed on 4 November, including a rerun with deterministic encoders. Earlier CPU runs produced seven vectors from three synthetic assets, then zero new vectors. Earlier preservation checks compared original Chroma hashes/counts and S3 keys, sizes and ETags without rebuilding the reference. Native retrieval and RAG evidence is separately dated.

\subsection*{Automatic checks and reproducibility limits}
GitHub Actions runs after pushes and pull requests. Windows/Linux jobs install the same requirements, check style and run offline tests with a 60\% coverage floor. Linux also tests isolated S3 storage. That floor detects large regressions, not overall quality. All three jobs passed for commit \texttt{2f91480}.\footnote{\href{https://github.com/SambhavMayani/ADSBDB/actions/runs/40944329385}{GitHub Actions run 40944329385}, completed 29 October 2026. Recheck the final submitted commit.} JUnit and coverage reports are retained as artifacts.

A clone reproduces the tests and synthetic demonstration. The 198-file reference also requires the data handoff, metadata and pinned model cache, since new downloads may change. Query copies become stale, long audio can use substantial RAM and text duplicate comparisons are quadratic. We have no labelled retrieval or biological benchmark. Our priority was an inspectable, recoverable implementation with evidence for its guarantees.

\subsection*{A possible extension beyond P1}
We considered the JEPA family as extra work, but left it outside P1 because of time and course scope. VL-JEPA predicts text embeddings and decodes words when needed. Its paper reports 2.85 times fewer decoding operations in its selective-decoding experiment, not that saving for our whole pipeline.\footnote{Chen et al., \href{https://arxiv.org/abs/2512.10942v2}{VL-JEPA}, February 2026 revision.} A future version could test visual candidate matching or camera-trap video retrieval before requesting an explanation. We would need new compatible vectors, wildlife relevance tests and CPU/RAM measurements. It would not automatically replace source retrieval and citation checks.
